- 칸의 조작 가능 여부와 아이템 종류를 분리해서 인식한다.
- 레벨 숫자가 있는 잠긴 칸은 locked로 처리한다.
  정확한 숫자를 읽지 못해도 보드 전체를 인식 실패로 처리하지 않는다.
- 실제 아이템을 일괄 unknown으로 분류하지 않는다.
- 잠긴 칸이나 정체를 모르는 칸이 많다는 이유만으로 보드를 거부하지 않는다.
- 합성은 조작 가능한 칸에서 동일 종류·단계로 확인된 아이템끼리만 수행한다.
- 생성기로 확인된 대상만 더블 탭한다. 임의의 아이템을 생성기로 가정하지 않는다.
- 생성기는 물체에 붙어 있는 하늘색 번개(에너지) 표시로 식별한다. 화면 상단의 에너지 잔량 표시는 생성기 표시와 구분한다.
- 생성기로 확인된 물체만 더블 탭하여 아이템 생성을 시도한다.
- 더블 탭 후 애니메이션이 끝난 화면을 다시 관찰해 새 아이템이 생겼는지 확인한다. 입력 실행 성공만으로 생성 성공을 판단하지 않는다.
- 빈칸과 에너지가 충분한데도 새 아이템이 생성되지 않으면 해당 생성기가 쿨타임 중일 가능성이 있다고 판단한다. 즉시 반복 탭하지 않고 다른 가능한 합성을 진행하거나 기다린 뒤 재시도한다.
- 에너지 부족이나 빈칸 부족을 쿨타임과 구분한다. 확인되지 않은 쿨타임 길이를 임의로 단정하지 않는다.
- 보드의 파란색 타일은 빈칸의 배경이다. 파란색이나 채도가 있다는 사실만으로 아이템으로 분류하지 않는다.
- 파란 타일 배경만 보이고 그 위에 별도의 물체 형태·윤곽이 없는 칸은 empty로 분류한다. 이런 칸을 합성할 아이템 목록에 넣지 않는다.
- 파란색 아이템도 존재할 수 있으므로, 칸의 대표 색상만으로 empty를 결정하지 않는다. 타일 배경과 구분되는 물체의 존재를 먼저 확인한다.
- 합성 스와이프는 시작 칸과 도착 칸 모두에 실제 아이템이 있고, 두 아이템의 종류와 단계가 같다고 판단될 때만 수행한다.
- 두 칸의 배경색이나 색상 히스토그램이 같다는 이유만으로 동일 아이템이라고 판단하지 않는다.
- 회색으로 흐리게 표시되고 하단에 분홍색 체크무늬 천이 덮인 아이템은 잠긴 아이템이다. 빈칸이나 일반적으로 이동 가능한 아이템으로 취급하지 않는다.
- 잠긴 아이템은 드래그의 시작 대상으로 선택하지 않는다.
- 잠금을 해제하려면 이동 가능한 동일 종류·동일 단계의 아이템을 잠긴 아이템 위로 드래그한다. 이 경우 잠긴 칸은 도착 대상으로 사용할 수 있다.
- 동일 아이템 여부는 물체의 형태·윤곽·세부 특징으로 확인한다. 색상이 같거나 색상 히스토그램이 비슷하다는 이유만으로 같은 아이템이라고 판단하지 않는다.
- 잠금으로 인한 회색 처리와 체크무늬 천은 아이템 자체의 특징과 구분한다. 가려진 부분 때문에 종류나 단계를 확실히 식별하지 못하면 잠금 해제 동작을 추측해서 수행하지 않는다.
- 레벨 숫자가 표시된 잠긴 칸과 체크무늬 천이 덮인 잠긴 아이템은 서로 다른 상태로 분류한다. 동일 아이템을 올리는 해제 규칙은 체크무늬 천이 덮인 아이템에만 적용한다.
- 화면 상단 손님의 주문 카드에 표시된 음료를 만드는 것을 우선 목표로 삼는다. 주문 아이템의 종류·단계를 확인하고, 해당 아이템을 얻는 생성·합성을 우선한다.
- 주문에 필요한 아이템이 완성되면 불필요하게 추가 합성하지 않고 판매를 우선한다.
- 주문 카드의 아이템 배경이 초록색으로 바뀌고, 손님에게 초록색 체크 버튼이 나타나면 판매 가능한 상태로 판단한다. 초록색 배경만으로 판매 가능 여부를 단정하지 않는다.
- 판매 가능한 손님의 체크 버튼을 탭해 주문을 완료하고 코인을 받는다. 보드의 음료를 탭하는 동작과 구분한다.
- 판매 후 주문 변경·아이템 소모·코인 증가 등의 변화를 확인한다. 입력이 실행됐다는 이유만으로 판매 성공으로 기록하지 않는다.
- 행동 우선순위는 판매 가능한 주문 완료 → 주문 음료를 위한 합성 → 필요한 아이템 생성 순서다.

## 손님 주문 판매: 보드 밖 탭 예외

- Tasty Travel의 solver는 B 화면의 격자 조작뿐 아니라 보드 위 손님 영역의 판매 체크 버튼 탭도 담당한다. 판매 가능한 주문 완료를 합성·생성보다 우선한다.
- observe()는 현재 화면에서 판매 체크 버튼의 좁은 픽셀 경계를 찾아 `order_controls`에 기록한다. 각 항목은 `id`, `bbox`, `ready`, `checkmark_visible`, `order_background_green`을 포함한다.
- 예: `{"id":"order_1","bbox":[150,80,250,140],"ready":true,"checkmark_visible":true,"order_background_green":true}`. 예시 숫자를 하드코딩하지 않고 현재 해상도와 실제 버튼 위치에서 구한다.
- 체크 버튼과 그 손님의 초록색 주문 아이템 배경이 모두 확인될 때만 ready=true로 둔다. 단순한 초록색 영역이나 보드 아이템을 판매 버튼으로 오인하지 않는다.
- 판매 동작은 `{"type":"tap","x":버튼중심X,"y":버튼중심Y,"duration_ms":80,"target":"sell_order","target_id":"order_1","reason":"판매 가능한 주문 완료"}` 형식을 사용한다.
- 버튼 경계는 이미지 안이고 보드 위에 있어야 한다. 버튼 크기는 화면 너비의 40%, 높이의 20% 이하로 제한한다. 실제 체크 버튼을 감싸는 좁은 경계만 제공한다.
- board_bbox와 grid는 실제 격자 영역만 나타낸다. 판매를 허용하려고 보드 범위를 손님 영역까지 확장하지 않는다. 보드 밖 스와이프·더블 탭은 허용하지 않는다.
- 주문 종류·단계와 판매 가능 상태를 observation의 상태 및 signature에 반영한다. 판매 후 변화가 확인되지 않으면 같은 버튼을 무작정 반복 탭하지 않는다.

## 잠금 검증을 위한 출력 계약

- `grid.access`에 각 칸을 `available`, `locked`, `unknown`으로 기록한다. 천으로 덮인 아이템과 숫자 레벨 잠금은 모두 `locked`이며, 드래그 시작점으로 사용하지 않는다.
- `grid.unlockable`은 동일 종류·동일 단계의 열린 아이템을 올려 해제할 수 있는 천 잠금만 `true`로 둔다. 숫자 레벨 잠금과 불확실한 칸은 `false`다.
- `grid.labels`에는 아이템 종류와 단계를 함께 기록한다(예: `iced_tea_2`). 색상만으로 동일성을 주장하지 않는다. 빈칸은 `empty`, 정체가 불명확하면 `unknown`이다.
- 실행기는 시작점의 조작 가능 여부와 도착점의 잠금 해제 조건을 검사한다. 이 필드가 없는 기존 solver의 보드 입력은 복구 경로로 넘긴다.
- 보드 진행 판단은 아이템 종류·단계 및 잠금 상태 변화에 근거한다. 색상 히스토그램, 선택 테두리, 반짝임, 좌표 미세 변화만으로 합성 성공으로 판정하지 않는다. 상태 변화가 있다고 해서 주문 완료나 게임 클리어를 의미하지도 않는다.

## GUI 실행과 보드 solver 역할

- `configs/gui_rules/tasty_travel.yaml`에 등록된 판매·튜토리얼 닫기는 공통 실행기가 먼저 확인하고 GUI Actor로 실행한다. 해당 파일이 제공된 생성 요청에서는 이 버튼들의 색상 탐지·판매 탭 코드를 solver에 다시 구현하지 않는다.
- solver는 주문 목표를 참고한 보드 인식·합성·생성에 집중한다. 등록된 GUI 규칙이 현재 화면에 적용되지 않으면 기존 로컬 solver/복구 경로로 진행한다.
